# Images, icons and fonts

Three places hold static files, and which one you pick is decided by _how the file
is referenced_, not by what kind of file it is.

| Where                   | For                                                              | How it is referenced                            |
| ----------------------- | ---------------------------------------------------------------- | ----------------------------------------------- |
| `src/assets/`           | Anything a component imports — icons, illustrations, local fonts | `import logo from '~/assets/images/logo.png'`   |
| `public/`               | Files that need a fixed, guessable URL                           | `/manifest.webmanifest`, `/docs/terms.pdf`      |
| `src/app/` (file names) | Favicons, app icons, OG and Twitter images                       | Nothing — Next writes the `<head>` tags for you |

The rule of thumb: **if a component references it, it belongs in `src/assets/`.**

Everything in `src/assets/` goes through the bundler, which means a content hash in
the filename (so it can be cached forever), a build error when the file is missing
or renamed, `width`/`height` inferred at build time for images, and dead assets
dropped from the output. `public/` gives you none of that — a typo in a `public/`
path is a 404 at runtime, on the one page nobody opened before release.

`public/` is for the handful of files where the _URL itself_ is the contract:
something a third party fetches (`/manifest.webmanifest`, a verification file a
payment provider or Google asks you to host), a document you link to by a stable
address, or a service worker that must be served from the origin root. This repo's
only inhabitant today is `mockServiceWorker.js`, generated by MSW for exactly that
reason.

```
src/assets/
├── icons/        interface glyphs — become React components (see below)
├── images/       raster art: photos, illustrations, empty states
└── fonts/        local font files, only when next/font/google is not an option
```

## Icons: SVG that becomes a component

Every SVG in `src/assets/icons/` is compiled by [SVGR](https://react-svgr.com/) into
a React component, and reaches the app through
[`components/ui/Icon`](../src/components/ui/Icon/Icon.tsx):

```tsx
import { Icon } from '~/components/ui/Icon/Icon';
import { Icons } from '~/components/ui/Icon/types';

<Icon type={Icons.Search} size={16} />                 {/* decorative */}
<Icon type={Icons.Search} title={t('search')} />       {/* is the label */}
```

An inline `<svg>` rather than `<img src="/icons/search.svg">` buys two things that
matter: it inherits `color` from its parent — so a theme token drives it and dark
mode needs no second file — and it costs no extra request. The price is bundle
size, which is why this path is for interface glyphs only. A logo, an illustration
or anything above a few kB is an image, not an icon.

### Adding one

1. Drop `foo.svg` into `src/assets/icons/`.
2. Add `Foo` to the `Icons` enum and the `IconsMap` in
   [`components/ui/Icon/types.ts`](../src/components/ui/Icon/types.ts).

That is all. `IconsMap` is typed `Record<Icons, …>`, so an enum member without a
component is a type error rather than a blank space in the UI, and the
[Icon story](../stories/components/ui/Icon/Icon.stories.tsx) picks the new glyph up
without being edited — it is the icon catalogue, so _"do we already have a check
mark?"_ is a Storybook search rather than an `ls`.

`Icon` is the only module in `src/` that imports from `~/assets/icons/`. Keep it
that way: an icon set is manageable as one map and unmanageable as a hundred
imports spread across features.

### Two constraints on the SVG file itself

**Import through the `~` alias**, never a relative path. The type declaration in
[`src/types/svg.d.ts`](../src/types/svg.d.ts) matches `~/assets/icons/*.svg`;
`../../assets/icons/foo.svg` falls through to Next's `*.svg` → `any` and you lose
every prop check silently.

**Colour has to come from `currentColor`.** Icons in this template already do.
Figma exports do not — they carry a hard-coded near-black fill, so
`svgr.config.js` rewrites `#0B0B0C` → `currentColor` at build time. If your design
system exports a different black, change that one value rather than editing SVG
files by hand. An icon with a baked-in `fill="#111"` looks correct until someone
switches to dark mode.

### Tinting an icon

By default an icon inherits `color` from its parent — style the container, not
the icon, and a theme token drives it. When the icon must differ from the text
next to it, `Icon` takes two props:

```tsx
<Icon type={Icons.Check} strokeColor="var(--color-success)" />
<Icon type={Icons.Search} strokeColor="var(--color-danger)" fillColor="var(--color-bg-subtle)" />
```

- `strokeColor` (default `currentColor`) rides the `currentColor` channel — the
  strokes, the way these glyphs are authored. The default means "inherit", so
  existing call sites behave exactly as before.
- `fillColor` (default `transparent`) is the root `fill`, inherited by every
  shape that does not hard-code its own — it paints the interior that the
  authored `fill="none"` leaves empty.

Both land as SVG _attributes_, not inline styles, so CSS passed via `className`
still outranks them. A multicolour glyph with baked-in fills ignores both props;
that is a property of the file, not something `Icon` can override.

### `Icon` is not clickable

Deliberately, unlike the equivalent in `react_zd_v1`. A clickable icon needs a focus
ring, a keyboard handler and an accessible name; wrapping it in a `Button` gets all
three, and a `<div onClick>` gets none of them.

`title` is the accessible name and, like everything in `components/ui`, arrives
**already translated** — no `t()` in the UI kit. Omit it whenever the icon sits next
to text that already says the same thing; the icon is then `aria-hidden`, which is
what you want. A screen reader announcing "chevron" is noise.

## Raster images: `next/image`, always

Never a bare `<img>`. `next/image` does format negotiation (AVIF/WebP), generates a
`srcset`, reserves layout space so the image cannot shift the page, and lazy-loads
below the fold. All of that is opt-out, not opt-in.

**Local images are imported, and then `width`/`height` are unnecessary** — Next
reads them from the file and can generate a blur placeholder:

```tsx
import Image from 'next/image';

import emptyCart from '~/assets/images/empty-cart.png';

<Image src={emptyCart} alt="" placeholder="blur" />;
```

**Remote images need explicit dimensions and an allowlist entry.** The pattern the
reference feature already uses — see
[`ProductCard`](../src/features/catalog/ProductCard/ProductCard.tsx):

```tsx
<Image
  src={product.thumbnail}
  alt={product.title}
  width={320}
  height={320}
  sizes="(max-width: 600px) 50vw, (max-width: 1000px) 33vw, 240px"
/>
```

Three rules that are not style preferences:

- **`sizes` is required for any image that is not a fixed pixel size.** Without it
  Next serves the largest candidate in the `srcset` to every viewport. This is the
  single most common cause of a "why is our LCP four seconds" report.
- **`priority` on the one largest above-the-fold image, and nowhere else.** It opts
  the image out of lazy loading so the browser does not discover it after
  hydration. Two or three `priority` images on a page cancel each other out.
- **`alt=""` for decorative images, a real sentence for meaningful ones.** Empty is
  a correct answer; missing is not.

Every remote host has to be listed in `images.remotePatterns` in
[`next.config.ts`](../next.config.ts). This is an allowlist rather than a
convenience: without it, the optimizer would fetch, resize and cache an image from
any URL that turns up in an API response — a bandwidth bill and an SSRF surface
with the same root cause. The template ships `cdn.dummyjson.com` because that is
where the demo API's product images live. Replace it.

For user-uploaded content on a domain you cannot enumerate, the answer is a
signed-URL host you _can_ enumerate — not a wildcard pattern.

## Favicons, app icons and OG images

These are Next **file conventions**, not imports and not `public/` files. Drop the
file in `src/app/` with the right name and Next emits the `<head>` tags, the
content hash and the `sizes`/`type` attributes:

| File                                       | Effect                                     |
| ------------------------------------------ | ------------------------------------------ |
| `src/app/favicon.ico`                      | `<link rel="icon">` — root of `app/` only  |
| `src/app/icon.svg` / `icon.png`            | modern browser tab icon                    |
| `src/app/apple-icon.png`                   | iOS home screen (180×180)                  |
| `src/app/[locale]/opengraph-image.png`     | `og:image` for every page under the locale |
| `src/app/[locale]/opengraph-image.alt.txt` | its alt text                               |

`favicon.ico` is the one with a location constraint — it must sit at the top level
of `app/`, not inside `app/[locale]/`. Everything else can live in any segment and
applies to that segment's subtree, which is what makes a per-route OG image cheap.

Putting a favicon in `public/` also works and is what most guides from the Pages
Router era say. Don't: you then own the `<link>` tags by hand, and lose the hashing,
so a favicon change takes a cache generation to show up.

## Fonts

`next/font` in the locale layout — self-hosted, preloaded, no external request, no
layout shift. Details and the Arabic caveat are in
[theming.md](./theming.md#fonts).

`src/assets/fonts/` exists for the case `next/font/google` cannot cover: a licensed
face you host yourself. Then it is `next/font/local` pointed at the file, still not
a raw `@font-face`, so you keep the preloading and the `size-adjust` fallback
metrics that prevent the swap from shifting layout.

Do not put font files in `public/`. A `@font-face` with a `public/` URL is
unhashed, unpreloaded, and re-downloaded on every deploy.

## How the SVG pipeline is wired

Worth knowing before you debug it, because it lives in **three** bundler configs and
they must agree. The options themselves are in one file,
[`svgr.config.js`](../svgr.config.js), imported by all three:

| Config               | Bundler   | Registers                            |
| -------------------- | --------- | ------------------------------------ |
| `next.config.ts`     | Turbopack | `@svgr/webpack` in `turbopack.rules` |
| `vitest.config.ts`   | Vite      | `vite-plugin-svgr`                   |
| `.storybook/main.ts` | Vite      | the same plugin, inside `viteFinal`  |

Vitest and Storybook never load `next.config.ts`, so each needs its own
registration. Miss one and the failure is confusing in proportion to how far it is
from the config: the app works, and only the test run — or only Storybook — renders
a broken element, pointing at the component rather than at the bundler.

**The rule is scoped to `src/assets/icons/`.** A blanket `'*.svg'` rule turns
_every_ SVG in the repo into a React component, which breaks `next/image` static
imports, CSS `url()` and anything else expecting a URL string. In `next.config.ts`
that scoping is a `condition.path`; on the Vite side it is the plugin's `include`.
Both read the same pattern from `svgr.config.js`.

Three details in that file are load-bearing:

- **`exportType: 'default'`, and no `?react` suffix on imports.** The suffix is a
  Vite convention — it is what `vite-plugin-svgr` defaults to and what its README
  shows — and it does not survive the trip to the other two consumers: an
  `import … from '…svg?react'` needs its own Turbopack condition _and_ its own
  ambient module declaration, because neither `~/assets/icons/*.svg` nor Next's
  `*.svg` matches a specifier with a query. One import spelling that works
  everywhere beats matching the upstream README.
- **`removeViewBox: false`.** SVGO drops `viewBox` when the source has `width` and
  `height` — which Figma exports do. `Icon` sets both from its `size` prop, so
  without the viewBox a resized glyph is cropped instead of scaled, and it still
  looks right at the authored 24px. This one only bites in the Next build:
  `vite-plugin-svgr` runs SVGR's JSX plugin alone and never invokes SVGO, so
  Vitest and Storybook cannot catch it. Check it with the `grep` below.
- **`as: '*.js'` in the Turbopack rule.** It tells Turbopack the loader returns
  JavaScript. Without it the output is treated as an asset again and the rule
  silently does nothing.

A `webpack()` block does nothing here — Turbopack is the bundler in Next 16. That is
the trap when copying an SVG setup from a Next 14 project.

### Storybook needs one more line than the other two

`@storybook/nextjs-vite` emulates `next/image`'s static imports with a plugin that
claims **every** image extension — SVG included — in `resolveId`, redirecting it to
a virtual module exporting `{ src, width, height, blurDataURL }`. It intercepts one
hook earlier than `vite-plugin-svgr`'s `load`, so it wins regardless of plugin
order, and registering SVGR is not enough on its own. Hence:

```ts
framework: {
  name: '@storybook/nextjs-vite',
  options: { image: { excludeFiles: [ICONS_GLOB] } },
},
```

Two things about that line. The key is **`excludeFiles`**, not `exclude` — the
option is called `exclude` in `vite-plugin-storybook-nextjs`'s README and
`excludeFiles` in its types and implementation (v3.3.2); the README spelling is
accepted and silently ignored. And the symptom, if you get it wrong, is that the
Storybook build **succeeds** and every Icon story is broken at runtime, because a
story is only evaluated when someone opens it.

## Checking your work

```bash
pnpm test run __tests__/components/ui/Icon    # the transform ran under Vite
pnpm build                                     # …and under Turbopack
```

If SVGR did not apply, an icon import is a URL string and React is handed a string
where it expects a component. Two ways to see it directly after a build:

```bash
find .next -name "*.svg"        # an icon here means it fell back to a URL
grep -rl "0 0 24 24" .next/static   # a viewBox here means it was inlined
```
